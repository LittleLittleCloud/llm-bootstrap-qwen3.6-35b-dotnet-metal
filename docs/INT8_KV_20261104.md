# Optional INT8 target KV: implementation and native controls

This report preserves the initial K128 implementation and its measurements.
The subsequent [30K tuning](INT8_30K_PREFILL_20261104.md) selects an optimized
K256 kernel and reverses the 30K regression in matched native controls. Storage
and quantization are unchanged; the tuned preset still defaults to FP16 KV.

The target engine now supports `--kv-cache-precision int8`. This is an experimental storage option, not a faster default. The matched native controls do not show a prefill speedup over the current FP16 path, so `--tuned-prefill` continues to use FP16 KV. The earlier Splash KV-only gain did not transfer to this implementation.

## Storage and execution

- Target K and V are symmetric signed INT8, rounded to nearest-even and clamped to [-127,127]. Each token/head has separate FP32 K and V scales over 256 dimensions. Zero vectors use zero codes and zero scales.
- K remains token-major. V is transposed within 256-token pages, independent of cache capacity, so growth preserves byte offsets. V allocations round up to a full page; scale allocations cover actual capacity.
- Q/K normalization, RoPE, gate extraction, query packing and KV quantization share the fused preparation dispatch. The unfused path also supports batch and single-token writes.
- Prefill uses direct device INT8 TensorOps operands: FP16 Q × INT8 K, then BF16 scaled probabilities × INT8 V, with FP32 destinations and online statistics. Key scales apply before softmax; value scales apply to probabilities before PV. No full-history dequantization workspace is allocated. The INT8 PV descriptor permits relaxed precision; the FP16 control retains its original descriptor.
- BF16 scaled probabilities prevent the FP16 underflow exposed by scaling the test V vectors down by 1e-6. Query precision stays FP16. Kernel tests bound probability-rounding error by the BF16 half-ULP relative bound (2^-8) times the weighted absolute values, plus an FP32 arithmetic allowance.
- The selected tile has 32 grouped query rows and 128 keys, eight SIMD groups and eight query heads per KV head. The former 32×256 tile remains available in the kernel diagnostic. Larger/smaller query tiles, a token-major V prototype and a separate contiguous probability scratch did not improve the microbenchmark.
- Serial decode and speculative verification read INT8 directly using FP32 scalar arithmetic. They do not reinterpret INT8 bytes as FP16/FP32 or expand the history.
- Draft KV stays FP16 when target KV is INT8. Target FP32 and FP16 continue to select matching draft storage.
- Cache growth copies codes and scales; reset clears both. Prefix checkpoints share the valid KV lineage, and verification rollback overwrites rejected positions before reuse. The diagnostic state hash covers only consumed V slots within partial pages and includes K/V scales.

At 32768-token capacity, ten full-attention layers require **640 MiB FP16 target KV versus 325 MiB INT8 plus scales**, saving **315 MiB (49.22%)**. This excludes weights, draft KV, recurrent state, prefix snapshots and attention scratch. It is not a 49% reduction in total model memory.

INT8 selects its direct online prefill kernel independently of the legacy `--attention-mode` selector; serial/verification use its FP32 reader. This is a target-cache precision experiment, not a change to weights or recurrent-state precision.

## Measurement procedure

Apple M5 Pro, 20 GPU cores, 48 GiB, macOS 26.6.2. Base engine commit `41f8e470efc1e4628a467936eddcbdd618be1d3f`, plus this worktree change. Official FP8-derived affine-8 group-64 v2 weights, BF16 expert output, BF16 DFlash2 weights, FP16 draft KV, staged8 DeltaNet, fused preparation, dispatch mask 29, 2048-token chunks and 32768 context.

The same 10,520-token and 29,939-token retrieval prompts are used in every process. Loading and tokenization are excluded from wall timing; first-token computation, draft context setup and creation of prefix snapshots are included. Prefix reuse is cleared for every measured request. Runs are serial: FP16 before, INT8, FP16 after. Each process performs one first-use request, three uninstrumented warm requests and a separate counter request at each length. Wall results use warm medians; counter intervals can overlap and are not additive wall costs. This is a native diagnostic, not the repository-owned endpoint evaluation or a new Splash ranking.

The initial FP16-scaled-probability prototype already showed no speed gain: 10K INT8 3774.600 ms versus FP16-after 3754.044 ms; 30K 12702.887 versus 12491.764 ms. Its local evidence is retained under `artifacts/int8-kv/full-profile/`. The final path uses BF16 probabilities for the numerical-range reason above.

## Final native prefill results

| Input tokens | FP16 before, ms | FP16 after, ms | INT8, ms | INT8 vs FP16-after latency | FP16 / INT8 tok/s |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10,520 | 3744.261 | 3746.206 | 3777.509 | +0.84% | 2808.17 / 2784.90 |
| 29,939 | 12510.082 | 12487.962 | 12735.363 | +1.98% | 2397.43 / 2350.86 |

All six measured warm windows have zero new whole-machine swap-outs; all three complete processes also have zero new swap-outs and no recorded thermal warnings. Existing swap usage and small swap-ins remain, so this is not a claim that the machine had no memory pressure. FP16-before/after are close and bracket the INT8 process.

Counter intervals for attention plus preparation rise from **464.4 to 500.5 ms at 10K**, and **3465.9 to 3701.4 ms at 30K** (FP16-after versus INT8). The extra attention work is consistent with the wall regression. It does not establish how much is attributable to scale loads versus mixed-type matmul or online reductions; those were not separately isolated. Other layers also receive numerically changed activations/routes. Counter-request wall overhead ranges from 0.29% to 2.80% across these six cases.

Dispatches are **7218 → 7198 at 10K**, **16344 → 16324 at 30K**. The 20-count reduction comes from two fewer attention dispatches in one short tail across ten full-attention layers. Large prefill blocks retain the fused preparation and online-attention dispatch structure. Quantizing KV does not eliminate thousands of dispatches.

Keep the FP16 default for speed. INT8 currently trades a small prefill slowdown for 315 MiB less target KV at 32K. Further work on this route would need a materially better attention kernel, not just narrower storage. The earlier profile's dense preparation and MoE costs remain independent optimization candidates.

## Numerical and state validation

The INT8 kernel diagnostic covers eight history/query shapes, including single-token input, 7/31/32/33-row tails, page boundaries, 4093-token history and a 30000-token history. It checks independent CPU quantization and FP64 attention references, K/V zero vectors and outliers, prefix/tail guards, in-place output, scalar verification reads, and bitwise fused-vs-separate normalization/RoPE/quantization. The final tested arithmetic maximum is **0.001152** relative to FP64 attention on the already-quantized cache. Quantization itself contributes up to **0.006646** against an FP16 cache in these synthetic samples; these are separate error sources, not whole-model accuracy scores. The tiny-V scale-invariance check passes with BF16 probabilities.

Paired real-model checks cover seven fixtures in serial and DFlash modes (14 comparisons, 28 successful full answers across precisions). Generated token sequences and first-token top-1 match FP16 in all 14 comparisons. Maximum first-token softmax KL is **5.045e-5 nats**, maximum total variation **0.000297**; top-10 overlap ranges from 8 to 10. Centered logit relative L2 ranges from 4.88% to 14.80%, so the raw logits are not close in every metric even though these high-confidence answers and probability distributions are stable. This small probe set does not replace broad quality evaluation.

The INT8 cache regression passes 45 speculative verification/rollback checks and 48 prefix-cache checks, including branching, shortening, cancellation, exact block boundaries, sequential prefill and append through capacity growth. Long retrieval checks additionally exercise both early and late needles, repeated cached generation and a short request after 32K growth.

Metal shader validation passes all eight INT8 cases with no reported GPU validation errors. The FP16-probability negative control fails the tiny-V check as intended, while the final BF16-probability path passes. Existing FP16/FP32 storage diagnostics pass 45,160 checks, and all 12 selected FP16 online-attention cases pass their CPU references (nine online cases also match the original r1 kernel bitwise).

## Reproduction

```sh
dotnet build src/Bootstrap.Engine -c Release -o artifacts/int8-kv/bin
dotnet artifacts/int8-kv/bin/Bootstrap.Engine.dll int8-kv-self-test
python3 scripts/profile-int8-kv.py \
  --dll artifacts/int8-kv/bin/Bootstrap.Engine.dll \
  --model-dir /path/to/pinned/FP8 \
  --draft-dir /path/to/pinned/DFlash2 \
  --affine-cache /path/to/affine8-g64-v2 \
  --prompt-file /path/to/prompt-10k.txt \
  --long-prompt-file /path/to/prompt-30k.txt \
  --out artifacts/int8-kv/new-evidence --phase all
python3 scripts/summarize-int8-kv.py artifacts/int8-kv/new-evidence
```

The paired quality fixtures expect access code `73DY-DRV5-B8FJ` in the two supplied prompts, plus five fixed arithmetic, sorting, extraction, counting and correction probes. The runner preserves exact commands, source/binary/prompt hashes, raw logs, whole-machine memory/thermal samples and first-token logits. It refuses an existing evidence directory or a stale copied Metal source. `--phase profile`, `quality` and `cache` allow independent reproduction. Kernel-only attention diagnostics accept `--case history,rows` and `--tile 32,128` or `32,256`.

## Input-type follow-up

The [controlled attention type probe](ATTENTION_TYPE_PROBE_20261104.md) finds no meaningful complete-attention gain from changing Q to BF16. Direct mixed-type matmul is faster in its isolated controls; a unit-scale ablation instead identifies scale handling as a stronger lead. These diagnostic findings do not change the production default or the end-to-end results above.
